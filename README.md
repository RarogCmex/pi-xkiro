# pi-xkiro

Провайдер [xKiro](https://xkiro.com) (`https://api.xkiro.com/v1`) для [pi](https://pi.dev) с живым каталогом, учётом прав аккаунта и пулом ключей. npm-имя пакета — `@rarogcmex/pi-xkiro`.

> **In English.** pi-xkiro registers the **xKiro** gateway (`api.xkiro.com`) as a
> native pi provider. One `sk-xt-…` key opens a multi-vendor catalog
> (`openai/*`, `anthropic/*`, `z-ai/*`, `qwen/*`, `minimax/*`, `mistralai/*`,
> `deepseek/*`, `google/*`, `x-ai/*`, …) that describes itself: price in USD per
> 1M tokens, context window, output cap, vision/tools/reasoning flags and exactly
> the `reasoning_effort` levels each model accepts. The catalog is therefore read
> from `GET /v1/models` rather than hand-written; only a free-tier snapshot ships
> in the repo as an offline baseline. Install with
> `pi install git:github.com/RarogCmex/pi-xkiro@main`, authenticate with
> `/login xkiro` (or `XKIRO_API_KEY`). Free-tier quota is metered **per account,
> not per key**, which is why the plugin keeps a key pool. The rest of this README
> is in Russian; code comments and the npm metadata are in English. Note that
> every user-facing runtime string this plugin emits is also Russian, except three
> warnings in `keys.ts` — see «Обработка ошибок».

xKiro — шлюз «одна ручка — много вендоров»: 125 chat-моделей (`openai/*`,
`anthropic/*`, `z-ai/*`, `qwen/*`, `minimax/*`, `mistralai/*`, `deepseek/*`,
`google/*`, `x-ai/*`, …) за одним ключом `sk-xt-…` — число на 2026-09-24,
оно меняется в течение дня, — и каталог сам описывает
каждую модель: цену в USD за 1M токенов, окно контекста, лимит вывода,
флаги vision/tools/reasoning и **ровно те уровни `reasoning_effort`, которые
модель понимает**. Поэтому каталог здесь не пишется руками, а читается из
`GET /v1/models`; в репозитории лежит только снимок бесплатного уровня как
офлайн-база.

Ставится как обычное pi-расширение, никаких `models.json` не нужно.

## Установка

```bash
pi install git:github.com/RarogCmex/pi-xkiro@main
# или локально
pi install /path/to/pi-xkiro
# разово, для проверки (из каталога с исходниками)
pi -e .
```

Ключ:

```bash
/login xkiro                 # сохранит в ~/.pi/agent/auth.json
# или
export XKIRO_API_KEY=sk-xt-…
```

`/login` валидирует ключ у шлюза и сразу показывает, **что он реально
открывает**: почту аккаунта, план, остаток бесплатной квоты на сегодня и
число доступных моделей из каталога. Модель потом выбирается обычным
`/model`, глубина размышления — `/thinking`.

## Ключи × модели: главный факт этого шлюза

Бесплатный уровень тарируется **по аккаунту, а не по ключу** (проверено
`GET /v1/usage`, 2026-09-24). Несколько ключей одного аккаунта делят один
суточный счётчик; несколько ключей **разных** аккаунтов дают несколько
независимых счётчиков. Ключи в примере ниже — переменные окружения
`XKIRO_API_KEYS` / `XKIRO_API_KEYS_FILE`, а не файл в репозитории.

Отсюда два неочевидных следствия:

1. **Все ключи работают одинаково и открывают один и тот же бесплатный
   уровень** (37 id на момент замера 2026-09-24; к вечеру их стало 42 — число
   меняется в течение дня). Разницы «какой ключ с чем работает» нет — есть только
   независимые суточные счётчики: N аккаунтов дают примерно N × 500k–1M
   бесплатных токенов в сутки вместо 500k. Поэтому плагин держит **пул ключей**:

   ```bash
   export XKIRO_API_KEYS="sk-xt-first,sk-xt-second,sk-xt-third"   # или XKIRO_API_KEYS_FILE=/path/to/keys.json
   ```

   Работает это так (как это выяснилось на живом замере):

   * **внутри процесса** — сессия закрепляется за одним аккаунтом, чтобы не
     сбрасывать кэш промпта на апстриме; при 429/402 запрос переезжает на
     следующий ключ, а сам ключ «остывает»;
   * **между процессами** — закрепление не помогает: pi живёт один разговор на
     процесс, и свежий pi всегда брал бы первый ключ. Замер 2026-09-24: четыре
     параллельных `pi -p` с пулом из двух ключей отдали все 39 924 токена
     первому ключу, а второй не получил ничего. Поэтому на старте плагин
     опрашивает `GET /v1/usage` по каждому ключу и ставит в начало те, у
     которых больше остатка суточной квоты, а внутри «одинаково хороших»
     (разница < `BALANCE_BAND` = 25%) перемешивает — иначе одновременные старты
     снова сошлись бы на один. После фикса те же параллельные запуски легли на
     два аккаунта из четырёх (+30 085 и +34 046 токенов на два ключа, остальные
     не тронуты).

2. **Пополнение кошелька платные модели НЕ открывает.** В доках написано
   «requires an active paid plan or real deposited balance» — на живом аккаунте
   с ненулевым балансом кошелька `openai/gpt-5.6-sol`, `openai/gpt-6-sol`,
   `anthropic/claude-opus-5`, `z-ai/glm-5.2` и самая дешёвая платная
   `z-ai/glm-4.6v-flashx` ответили `403 permission_denied` ровно так же, как на
   нулевом балансе. Значит плагин доверяет только полю `plan`: без плана в
   `/model` попадают только `access_tier:"free"`, чтобы пи не предлагал заведомо провальные модели.

## Переменные окружения

| переменная | назначение |
|---|---|
| `XKIRO_API_KEY` | один ключ (используется и `/login`, и окружением) |
| `XKIRO_API_KEYS` | список ключей через запятую — пул аккаунтов (достаточно только его, `XKIRO_API_KEY` не обязателен) |
| `XKIRO_API_KEYS_FILE` | JSON-массив (`["sk-xt-…"]`) или `{"keys":[…]}`, перечитывается по изменению mtime |
| `XKIRO_KEY_ROTATION` | `off` — не вращать ключи, держать всё на первом |
| `XKIRO_TIERS` | `auto` (по умолчанию) / `free` / `free,paid` / `free,paid,premium` — руками расширить каталог без плана |
| `XKIRO_BLOCK_GATED` | `off` — не отсекать платные модели до запроса (по умолчанию отсекаются) |
| `XKIRO_BASE_URL` | зеркало/прокси (важно: путь должен оканчиваться на `/v1`) |

## Команда `/xkiro`

```
/xkiro            # каждый ключ: аккаунт, открытые уровни, остаток квоты сегодня,
                  # сколько ключей остывают после ошибок
/xkiro models     # каталог по уровням (free/paid/premium)
/xkiro reset      # снять закрепления сессий и остывание ключей
```

Материал ключа нигде не печатается: в статусе только короткий отпечаток
`хеш…4 символа`.

## Официальная документация

<https://docs.xkiro.com/> — два диалекта (`/v1/chat/completions` и
`/v1/messages`), плюс `/v1/responses`; `Authorization: Bearer` или
`x-api-key` взаимозаменяемы; `GET /v1/models` и `GET /v1/audio/voices`
публичные.

Ключевое из доков, что учтено здесь:

* **`/v1` обязателен в base URL** для OpenAI-диалекта: клиент дописывает
  `/chat/completions` сам. Наоборот (`/v1/v1/messages`) получается 404 — это
  единственный «говорящий» способ ошибиться.
* **Идентификатор модели всегда с префиксом вендора.** `gpt-5.6-sol` → 404,
  `openai/gpt-5.6-sol` → 200. Префикс не «нормализуется», это обязательная часть id.
* **`reasoning_effort` — не универсальный параметр.** ~половина каталога его
  игнорирует, наборы уровней различаются: `low..max`, `low,medium,high`,
  `none,high`, `off,on`, `adaptive,disabled`, `none,minimal,low..max`.
  Неизвестное значение не отклоняется, а **сбрасывается** (тогда включается
  дефолт модели, а это часто «включено»). Источник истины — поле
  `reasoning_efforts` в `GET /v1/models`, а не таблица в доках.
* **Блокирующий запрос режут на 95 секундах**, стриминг — нет. pi стримит
  всегда, поэтому плагин на это не натыкается, но руками (`curl` без
  `stream`) это видно.
* **Таблица статусов**: 400 `invalid_request` (в т.ч. отказ контент-политики —
  намеренно не 500, чтобы клиент не ретраил), 401 ключ, 402 нет средств,
  403 нет прав на модель, 404 нет модели, 429 лимит, 500/502/503/529 — шлюз.
  Повторять имеет смысл только 429/500/502/503.
* **Переполнение контекста шлюз считает сам**, до обращения к вензору: 400
  «Input is ~N tokens, which exceeds the safe limit of M tokens».

## Проверено руками (2026-09-24)

Полный журнал измерений — числа, ход отладки, что именно и на каких ключах
пробовалось — в [`research/2026-09-24-manual-probes.md`](research/2026-09-24-manual-probes.md).
Здесь только то, что меняет поведение плагина или ожидания пользователя.

* **На бесплатном уровне можно работать агентом.** Все id утреннего снимка (37)
  ответили на вызов инструмента. Но единичный отказ случается: один прогон дал
  `NO_CALL` на `minimax/minimax-m2.1-highspeed:free`, повтор — чистый. Отсюда
  правило, на котором стоит транспорт: **единичный отказ — случайность, а не
  свойство модели**, поэтому для агентной работы держите в пуле несколько ключей,
  а не выбирайте «лучшую» модель.
* **`capabilities.vision` и `capabilities.tools` — обещания шлюза, а не
  гарантии.** На них можно строить первичный фильтр, не больше.
* **Оба поля лимита принимаются** — `max_completion_tokens` и `max_tokens`;
  лимит честно отрабатывает (`finish_reason:"length"`). Зафиксировано
  `max_completion_tokens` (дефолт pi для незнакомых URL).
* **«Принято» ≠ «учтено».** Шлюз молчаливо терпит лишние поля: `store`,
  `prompt_cache_key`, `prompt_cache_retention`, `role:"developer"`, `strict:true`,
  `totally_unknown_field:123` — всё 200. Поэтому `compat` в `models.ts` включает
  только то, что удалось **наблюдать**, а не то, что просто не вызвало ошибку.
* **Маппинг уровней размышления работает end-to-end.** Замер через сам pi на
  `mistralai/mistral-medium-3.5` (шлюз публикует для неё только `none,high`):
  `--thinking off` → 0 символов мысли, `--thinking high` → 1 548 символов,
  которые pi показал как thinking-блоки. То есть `off` — честный выключатель, а
  «ступенька вниз» (`minimal`→`high` на двупозиционных моделях) — не догадка.
* **Мышление приходит как `reasoning_content`** — и в дельтах стрима, и в
  `message` без стрима; реплей ассистентского сообщения с `reasoning_content`
  принимается. Это родной для pi-ai формат, конвертировать в текст не нужно.
* **Визион работает, но не с любой картинкой.** Валидный 64×64 PNG распознают
  `qwen/qwen3-vl-plus:free`, `qwen3.8-max:free`, `qwen3.5-plus:free`;
  `minimax/minimax-m3:free` и `mistralai/mistral-small-2603` отвечают 200, но
  врут про цвет на таких мелких карточках. А **1×1 PNG** те же qwen-роуты
  заваливают `500 internal_error` (повторено на двух ключах). Для pi это не
  ловушка — вложения ресайзятся до внятных размеров, — но крошечные файлы да.
  Пробовать визон нужно **настоящими файлами**: самосборный base64 даёт `400
  Image … could not be loaded`, то есть провал самой пробы, а не шлюза.
* **`/v1/responses` и `/v1/messages` отвечают и для не-Claude моделей**
  (проверено на `qwen/*:free`, `minimax/*:free`) и намеренно не зарегистрированы:
  chat-completions покрывает весь каталог, а два лишних диалекта — вдвое больше
  форматов, которые надо держать проверенными.
* **Права на модели нельзя вывести из каталога.** Часть id с
  `access_tier:"premium"` (`tencent/hy4-preview`, `moonshotai/kimi-k3`,
  `x-ai/grok-4.5`, `minimax/minimax-m2.7`) отдаёт 503 на всех ключах — и на
  нулевом балансе тоже. Значит «503 вместо 403» — мёртвый роут, а не «права
  есть, но сломано»; по коду статуса отличить права от неработы нельзя. Отсюда
  доверие только к `plan`.
* **`sensenova/*` не соблюдает лимит вывода** и может не отвечать по 90 секунд.
  Бесплатно, но непредсказуемо по времени и расходу; обходится только выбором
  другой модели.
* **Каталог живёт в течение дня.** Утром 2026-09-24 было 120 id (37 бесплатных),
  вечером — 125 (42): добавились пять deepseek-id, ничего не исчезло. Поэтому
  снимок в `catalog.ts` — только офлайн-база, а числа в `/xkiro` и в тексте
  отказа берутся из живого листинга: захардкодить их — значит соврать через
  полдня.
* **Платная модель на бесплатном аккаунте отсекается до обращения в сеть.**
  `/model` её не показывает, но у pi есть обходной путь: `--model
  xkiro/openai/gpt-5.6-sol` на неизвестный id превращается в custom model и всё
  равно улетает в шлюз. Теперь транспорт решает по правам на каждый запрос
  (`selectKeysForTier`): бесплатная → идёт; платная и хоть один аккаунт пула с
  планом → закрепляется за ним; платная и все измеренные аккаунты без плана →
  отказ на месте, без round-trip. Ничего не известно (аккаунт не опрошен / id не
  из каталога) → запрос уходит как есть: **неопрошенный аккаунт — не отказ**.
  Отключается `XKIRO_BLOCK_GATED=off`. Доказательство «без сети» — локальный
  шлюз-логгер: на гейте он видел только `GET /v1/usage` и `GET /v1/models`, а
  `POST /v1/chat/completions` пришёл ровно на бесплатную модель и на прогон с
  выключенным гейтом (2 вызова на 3 запуска).


### Матрица бесплатного уровня (`node live/check.ts`, 2026-09-24)

**Один прогон по утреннему снимку — 37 id.** Вечером того же дня бесплатных id
стало 42, и закоммиченный снимок `catalog.ts` — вечерний; в нём 27 id с флагом
`vision` (17 `qwen/*`, 6 `mistralai/*`, 2 `sensenova/*`, по одному `minimax/*` и
`deepseek/*`). Числа ниже описывают прогон, а не текущий каталог. Читается
матрица как «что сломается, если положиться на поле каталога»:

| проверка | итог |
|---|---|
| обычный round-trip | 37/37 `200` |
| вызов инструмента | 37/37 в этом прогоне; в предыдущем один `NO_CALL` (`minimax-m2.1-highspeed:free`), который на повторе пропал |
| соблюдается ли лимит вывода | 35/37; **`sensenova/*` игнорирует** — два id, запрошено 5, отдано 688 и 210 токенов (в отдельном разовом замере тот же id дал 289; оба числа — разные прогоны, а не одна величина) |
| принимает ли `reasoning_effort` | 37/37 (у части моделей без контроля — молча нет) |
| vision, валидный 64×64 PNG | 25/25 — столько id несло флаг `vision` в утреннем снимке; все ответили 200 (одна ответила prose вместо слова) |
| vision, 1×1 PNG | **все 17 `qwen/*:free` → 500**; mistral/sensenova → 200 |
| стрим + usage-фрейм | 37/37 |

21 из 37 строк имели хотя бы одну неидеальную ячейку, и почти все они —
про 1×1 картинку, то есть про размер вложения, а не про модель. Вывод, который
важен для плагина: **`capabilities.vision` и `capabilities.tools` — это
обещания шлюза, а не гарантии**; на них можно строить только первичный
фильтр, а единичный отказ инструмента — случайность, не свойство модели.

## Каталог

`catalog.ts` содержит снимок бесплатного уровня (**42 id**, захвачен вечером
2026-09-24) — это офлайн-база, чтобы `/model` работал до первого обновления.
Живой `GET /v1/models` накладывается через `fetchModels` (pi сам кэширует
результат), и если обновление упало — каталог не сжимается, остаётся последний
успешный.

**Таблицы моделей в этом README намеренно нет.** Каталог здесь — не статический
список, а то, что шлюз отдал на последний запрос: id добавляются в течение дня
(см. «Проверено руками»), а цены, окна и уровни размышления шлюз публикует
помодельно. Захардкодить таблицу — значит соврать через полдня. Как посмотреть
актуальную:

| что | как |
|---|---|
| что доступно вам сейчас | `/model` внутри pi, или `pi --list-models xkiro` |
| что открывает ваш ключ (план, остаток квоты, число моделей) | `/login xkiro`, или `/xkiro status` |
| офлайн-снимок, с которым ставится плагин | `catalog.ts` (`FREE_TIER_SNAPSHOT`, 42 id) |

**Про цены.** Каждый id в закоммиченном снимке — бесплатный уровень, и у всех
`pricing.input`/`pricing.output` равны **0 USD за 1M токенов**: это значения
шлюза, а не заглушка. Цены платных уровней (`access_tier: "paid"` /
`"premium"`) приходят только из живого листинга и в снимке не представлены —
бесплатный аккаунт их не видит. Конвертация не нужна: шлюз сразу отдаёт USD.

Маппинг полей шлюза на `Model` pi:

| xKiro | pi |
|---|---|
| `id` (`vendor/model`) | `id` без изменений |
| `display_name` | `name`; для закрытых уровней дописывается `[paid]` / `[premium]` |
| `context_length` / `max_output_tokens` | `contextWindow` / `maxTokens`; отсутствие = 32 768 / 4 096 (доки: «absent means unknown, not unlimited») |
| `capabilities.vision` | `input: ["text","image"]` |
| `capabilities.reasoning` | `reasoning` |
| `pricing.input/output/cache_read/cache_write` | `cost.*` — USD за 1M, конвертация не нужна |
| `reasoning_efforts.levels` | `thinkingLevelMap` |
| `access_tier` | `filterModels` (в `Model` этого поля нет) |

Правила `thinkingLevelMap` (`catalog.ts`), чтобы уровень из pi превращался в
уровень, который шлюз **не выбросит**:

* `off` → собственное выключенное значение модели (`none` / `disabled` / `off`),
  а если его нет — `null`, и pi не предложит «выключить».
* точное совпадение → как есть;
* выше шкалы модели → ближайший доступный вниз (как и сам шлюз);
* ниже шкалы → **самый нижний положительный уровень**, а не «ничего»: на
  двупозиционных моделях (`off,on`, `none,high`, `adaptive,disabled`)
  проигнорированное значение шлюзом означало бы дефолт модели, то есть часто
  «совсем без размышления», чего пользователь не просил.
* *Модели без контроля (`reasoning_efforts` отсутствует), но с
  `capabilities.reasoning:true` получают `{ off: null }`: мысль приходит
  сама,рулить ею нельзя.

## Обработка ошибок

`errors.ts`, все переписания защищены условием `provider === "xkiro"` и
`stopReason === "error"`:

1. **Переполнение контекста** — «exceeds the safe limit of N tokens» не
   совпадает ни с одним шаблоном pi-ai (`/exceeds the limit of \d+/` — это
   формулировка Copilot, «safe» ломает матч), поэтому добавляется маркер
   `context_length_exceeded:` и срабатывает автокомпакция. Лимиты запросов
   (`429`, `quota`, `rate limit`) под переписание не попадают — иначе
   троттлинг выглядел бы как переполнение и запускал компакцию вместо повтора.
2. **403 уровня** — «требуется план или депозит» превращается в «модель
   платная, возьми бесплатную (`/xkiro`) или оформи план; повтор не поможет».
3. **402/429 квоты** — объясняет, что счётчик суточный и на аккаунт, и
   отсылает к `XKIRO_API_KEYS`.
4. **401** — ключ, а не модель: «проверьте ключ и `/login xkiro` заново».

Отдельно от переписывания — **пред-полётный отказ** (`selectKeysForTier` +
`gatedMessage` в `provider.ts`): там, где ответ шлюза уже известен по
измеренным правам, запрос не отправляется вовсе, а текст отказа собирает
живые числа (открыто N бесплатных, M аккаунтов в пуле).

## Транспорт и rotation

`index.ts` — **асинхронная фабрика**: перед `registerProvider` она один раз
балансирует шлюз (`balancePool`, `startupCatalog`). Это единственный
документированный способ повлиять на то, что видит `pi --list-models` и
`--model` на первом же запуске: pi не делает refresh каталога на этих путях, и
без ожидания `XKIRO_TIERS=free,paid,premium` упорно показывал только бесплатный
уровень вместо полного листинга (проверено). Любой сбой сети — `undefined`, и регистрируется снимок из
`catalog.ts`, а не пустой список.

`provider.ts::withKeyRotation` оборачивает адаптер pi-ai (сам адаптер
`openAICompletionsApi()` передаётся из `index.ts` — единственный символ из
compat-входа, см. комментарий там). Он же и реализует пул:

* ключ выбирается на запрос, сессия закрепляется за аккаунтом;
* HTTP-статус читается из `onResponse`, а не из текста ошибки — текст pi
  собирает человекочитаемый, ветвить по нему нельзя;
* **повтор на другом ключе возможен только пока ничего не видно юзеру**:
  ошибка до первого контент-события → следующий ключ; уже пошли токены →
  ошибку показываем как есть, а не переспрашиваем втихую;
* `aborted` (отмена пользователем) ключ не «остужает» и не ретраит;
* 403/404/400 на другой ключ не уводят — это не дефицит ёмкости;
* остывание: `quota` 5 мин, `rate` 60 с, `auth` 6 ч, `5xx` 5 с. Если остыли
  все — пул всё равно отдаёт ключи, чтобы протухший таймер не отрезал pi от
  живого шлюза.
* если пул пуст, а ключ pi передал через `options.apiKey` (например
  `--api-key`), он подсеивается в пул: одном ключевой сценарий работает ровно
  как без плагина.

## Разработка

```bash
node scripts/link-pi.mjs   # один раз: линкует пакеты pi из глобальной установки
npm run check              # typecheck + 87 офлайн-тестов (сеть не нужна)
node live/check.ts            # живой прогон: аккаунты + матрица free-уровня
node live/check.ts --snapshot # перегенерировать снимок каталога
node live/check.ts --surface  # перепроверить /v1/responses и /v1/messages
```

**Перепроверка на pi 1.0.0 (2026-10-03).** `--snapshot`: листинг читается, 129 chat-id,
из них free — 55 (столько же регистрирует плагин, см. замер дрейфа выше).
`--surface`: `POST /v1/responses` → 200 `pong`, `POST /v1/messages` → 200 `pong`,
`GET /v1/models` в anthropic-форме → 200, gated-модель верхнего уровня →
403 `permission_denied`. Полная матрица (`node live/check.ts` без аргументов) в тот
день **не гонялась намеренно**: это ~340 запросов при лимите 5 запросов/мин на
аккаунт, а у двух из пяти аккаунтов дневная бесплатная квота была уже выбрана —
прогон намерил бы троттлинг шлюза, а не поддержку моделей. Матрицу имеет смысл
повторять на свежей квоте.

**Предварительные условия.** Node ≥ 22.19 — нижнюю границу задаёт хост: `engines.node` у pi `>=22.19.0` (измерено и на 0.87.0, и на 1.0.0). Сам
type-stripping без флага и обнаружение `.ts`-тестов у `node --test` доступны
с 22.18.

Пакеты pi (`@earendil-works/pi-ai`, `@earendil-works/pi-coding-agent`,
`@types/node`) зависимостями не объявлены: в рантайме голый спецификатор
`@earendil-works/pi-ai` подменяет загрузчик расширений pi, поэтому обычный
`npm install` не даёт дерева, пригодного для тайпчека. Их линкует
`scripts/link-pi.mjs`: скрипт сам находит глобальную установку pi (префикс npm,
nvm, pnpm, `~/.local`, `/usr/local` или каталог, куда резолвится исполняемый
`pi`) и создаёт симлинки, на Windows — junctions. Для конкретного пути:
`PI_ROOT=/path/to/node_modules node scripts/link-pi.mjs`. Проверено на
pi 0.87.1 / pi-ai 0.87.1 / `@types/node` 22.19.19; тот же setup и `npm run check`
повторены на pi 0.99.1 / pi-ai 0.99.1 (2026-09-30) и на pi 1.0.0 / pi-ai 1.0.0
(2026-10-03) — в обоих прогонах 87/87 зелёные; загрузка на 1.0.0 проверена отдельно:
`pi -ne -e <репа> --offline --list-models xkiro` печатает каталог. Число моделей в
нём дрейфует вместе с listing'ом шлюза: 2026-09-30 было 63, 2026-10-03 — 55.
Причина измерена сегодня: `GET /v1/models` без ключа отдаёт 129 id, из них
`access_tier:"free"` ровно 55 — неопределяемый ключ означает бесплатный уровень,
поэтому печатается ровно столько. На 0.99.1 и 1.0.0 вывод совпадает: это дрейф
шлюза, а не pi.

`npm run typecheck` зовёт голый `tsc`, а `devDependencies` здесь намеренно пусты
(`scripts/link-pi.mjs` линкует только пакеты пи), поэтому TypeScript нужен в
`PATH`: `npm i -g typescript@5.9.3` — это версия, которую пиннит CI
(`.github/workflows/check.yml`); на 7.0.2 typecheck тоже чистый (измерено
2026-09-30).

Расширение опирается на свежие API хоста (`thinkingLevelMap`, `compat`,
`filterModels`, `createAssistantMessageEventStream`, контракт запуска
асинхронной фабрики расширений), при этом `peerDependencies` указан как `*` —
то есть минимальная версия pi не заявлена, и старый pi деградирует молча, а не
отказывается устанавливаться. Ориентир — 0.87.x, на нём проверено; на pi 0.99.1
и на pi 1.0.0 весь офлайн-набор тоже зелёный (2026-09-30 и 2026-10-03, по 87/87), и
на 1.0.0 проверена ещё загрузка расширения (`pi -ne -e … --offline --list-models
xkiro`). Это всё ещё проверка тестами и загрузкой, а не живым шлюзом: поведение на
старой или новой версии по-прежнему не заявлено.

**`live/check.ts` требует локальный, не публикуемый `secret.env`** рядом с
`live/check.ts` или в корне репозитория: строка `API=https://api.xkiro.com/v1`
(необязательна) и `KEY1=sk-xt-…`, `KEY2=…`, `KEYn=…` — по ключу на аккаунт.
Файла нет в репозитории (`.gitignore`), и без него скрипт **бросает исключение**
(`secret.env not found…` / `no KEY1..KEYn in secret.env`), а не падает молча.
Офлайн-тесты от него не зависят. Живой прогон тратит суточную бесплатную квоту
аккаунтов.

## Ограничения

По состоянию на 2026-09-24 — дату последних живых проб.

* **Платные модели не проверены на живом подписанном аккаунте.** Правило
  «`plan != null` → открыт `paid`/`premium`» — вывод из документации, а не из
  наблюдения. Единственный надёжный способ включить их сейчас — `XKIRO_TIERS`.
* **`capabilities.tools` у `:free`-вариантов — обещание, а не гарантия.** Один
  MiniMax из 37 id утреннего снимка инструменты не делает вообще, а единичный
  `NO_CALL` пропадал при повторе. Для серьёзной агентной работы это повод
  держать в пуле платный аккаунт.
* **Кэш промпта не проверен ни в одной форме** (`prompt_cache_key`, сессионные
  заголовки, `prompt_cache_retention`). Шлюз их принимает, но эффект наблюдать
  нечем — `cached_tokens` появляется и без них, поэтому отличить работу кэша от
  его отсутствия нечем. Соответствующие флаги в `compat` выключены: включить их
  можно только после замера с измеряемым эффектом.
* **`sensenova/*` не соблюдает лимит вывода** и может не отвечать по 90 секунд;
  обходится только выбором другой модели.
* **Стрим-ошибки не разбираются.** Случай `data: {"error":…}` после HTTP 200
  pi-адаптер не обрабатывает; на живом стриме проверена только успешная ветка.
  Если шлюз начнёт отвечать так массово, понадобится обёртка чтения потока.
* **`created` у всех id равен 1.** Дату создания модельных версий шлюз не
  публикует, поэтому поле непригодно ни для сортировки, ни для отсева.
* **Язык сообщений неоднороден.** README, все пользовательские строки рантайма
  (`errors.ts`, `provider.ts`, `index.ts`) и комментарии — на русском, при том
  что метаданные пакета (`description`, `keywords`) и три предупреждения в
  `keys.ts` — на английском. Пользователь, не читающий по-русски, получит
  русское сообщение об ошибке посреди сессии и не найдёт английского README.
  Это известная шероховатость, а не случайность: перевод всего рантайма —
  отдельная задача.
